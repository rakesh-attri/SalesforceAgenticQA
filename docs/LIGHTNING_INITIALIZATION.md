## Implemented evidence controls

The optional `initialization` field contributes to the locally approved diagnostic plan hash. Adding it to an old approval invalidates that approval. Removing it also blocks an already-created reader before dispatch and response projection. Its fixed scope permits the selected-app GET, six source buffers, at most 2,000,000 bytes per source and 8,000,000 total, request-shape fingerprints and reviewed selector counts. Oversized sources are skipped; traversal truncation is explicit. Neither source count/size nor observation time is expanded automatically.

Request evidence includes the native action hash, action count, query-key classification/count/fingerprint, recognized envelope keys and duplicate flags, exact parameter-key status, app-context kind/hash and framework-context hashes. It retains no parameter, cookie or token values, raw body, URL query values or page text. Unknown keys remain unknown. These fingerprints are evidence, not an executable request template.

Selected-app failures retain only a validated numeric HTTP status or a fixed unavailable diagnostic. Malformed JSON/provider body fragments are withheld; regression canaries cover both invalid JSON and HTTP failures.

Client-source parsing uses TypeScript ASTs without eval. It reports exact source hashes, bounded getCurrentApp anchors, nearby recognized calls, the known parameter key and directly observed return-value property reads. Missing anchors, partial traversal or unavailable sources never prove absence of behavior. Client expectations cannot establish server purity or a complete response schema. Raw source is not persisted or sent to Gemini.

Runtime progress distinguishes response headers from completed bodies, pending reviewed resources, failed requests explicitly denied by the framework, other navigation aborts and unclassified failures. Actual HTTP response status and finite client-error fingerprints remain separate. Error-pattern matching is not proof of causality or a Salesforce server defect. A denied request never becomes an application-error response in the report.
